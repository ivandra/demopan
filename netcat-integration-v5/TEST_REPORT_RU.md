# Проверка v5.1.1 на свежих данных — 1 ноября 2026

## Ошибка загрузки из GitHub: `.install/.htaccess`

В папке `files` предыдущего коммита отслеживались лишь 212 из 445 файлов. 233 ресурса, включая изображения, шрифты и видео, исключались `.gitignore` и присутствовали только в готовом ZIP. Теперь все 445 файлов отслеживаются Git. Это исправление самой поставки.

В отдельном Windows-сценарии старый checkout с `core.autocrlf=true` воспроизвёл тот же отказ на первом `.install/.htaccess`: файл существовал, но LF превратились в CRLF. Фактические байты файла с хостинга не получены; пользователь скачивал папку через веб-интерфейс и загружал через файловый менеджер. Поэтому CRLF не объявляется установленной причиной именно его серверного несоответствия.

Добавлено правило `.gitattributes` для поставки; Windows checkout сохраняет все 445 файлов побайтно. Проверка допускает лишь эквивалентные LF/CRLF в известных текстовых форматах. Загруженные файлы не переписываются. Изменённый код, изменённые директивы `.htaccess`, изменения файлов неизвестных форматов и повреждённые бинарные файлы по-прежнему отклоняются. Для изменённого файла выводятся размер и фактический SHA-256, для отсутствующего и недоступного — отдельные сообщения.

Проверены 10 сценариев настоящего верификатора на каждой версии PHP, включая отсутствие доступа под UID 65534. Полный цикл PHP 7.4.33 выполнен с CRLF в 294 файлах; PHP 8.3.36 — с исходными LF. Архив `*-upload.zip` содержит ровно те же 445 файлов в корне, что полная папка `files` и раздел `UPLOAD_TO_ROOT` полной поставки.

## Новый журнал хостинга: исчерпаны файловые дескрипторы

После публикации v5.1.1 пользователь предоставил журнал от 01.11.2026 20:00:37: перед `Failed opening required .../nc_page.class.php` стоят предупреждения `failed to open stream: Too many open files`. Непосредственная причина этой остановки установлена: исчерпание файловых дескрипторов процесса, а не сообщение о физическом отсутствии файла. Из лога нельзя определить, какие файлы или сокеты заняли лимит и есть ли утечка в конкретном серверном окружении. Повышение версии PHP не является доказанным исправлением.

Дополнительно проверены PHP 7.4.33 `cli-server` и PHP 7.4.33 `apache2handler` с OPcache и лимитом `nofile=64:64`. Естественное исчерпание лимита не воспроизвелось. В отдельном управляемом сценарии лимит был искусственно занят перед загрузкой `nc_page`: состояние на отметке 3564 файла не изменилось, а после освобождения ресурсов следующий запрос продолжил с 3572 файлов. Это проверка возобновления, а не доказательство происхождения занятых дескрипторов на хостинге. Подробности и порядок действий — [`docs/TOO_MANY_OPEN_FILES_RU.md`](docs/TOO_MANY_OPEN_FILES_RU.md).

Исходный v5 без правок был запущен на PHP 7.4.33 со свежим SQL и папкой `lifepodr3110`. Продолжение с сохранённой точки 3660/5666 завершило резервирование, установку и активацию. Файл `nc_page.class.php` в свежей папке существует и совпадает со старой копией. Это не устанавливает его состояние и доступность в момент ошибки на хостинге.

- Подтверждены Netcat 7.2.0, один сайт №1, компонент регионов №223, инфоблок №57, существующая региональная запись.
- Отдельные локальные копии: PHP **7.4.33** и **8.3.36**, MySQL **5.7.27**, режим PHP `cli-server`, Chromium / Playwright. У копий разные базы и каталоги. Внешние запросы и отправка писем отключены.

- PHP 8.3.36 в заголовке дампа относится к экспорту phpMyAdmin и не доказывает версию PHP сайта при сбое.
- Старый стенд v5 использовал PHP 8.3.36 и MariaDB 10.11. Его результаты нельзя подменять нынешними.

## Подтверждённые дефекты и исправления

1. **Откат на MySQL.** Старый v5 вставлял любое ненулевое значение как `X'hex'`. На MySQL 5.7 числовой идентификатор `1`, записанный как `X'31'`, стал `49`; следующий шаг отката перестал находить сайт №1. Проверено непосредственно: `X'31'+0 = 49`, `UNHEX('31')+0 = 1`. v5.1 использует `UNHEX`, сохраняет NULL и байты строк без повторного экранирования.
2. **Отсутствующий виджет.** В свежей базе и файлах нет виджета `regions`. Старый установщик без проверки пытался записать его шаблон в несуществующий каталог и затем сообщал об успешной активации. Теперь подстановки читают только разрешённые поля из существующей таблицы `Message223` / инфоблока №57; новый региональный компонент или виджет не создаётся. Запись файла функций проверяется по длине и SHA-256.
3. **Окно консультации.** Все кнопки объединялись группой Fancybox `consult` с одной inline-формой. Форма перемещалась в скрытый слайд. Кнопки теперь открывают одно окно без группировки. Исходные классы, HTML и CSS сохранены.
4. **Начало резервирования и время.** В свежей копии осталось незавершённое состояние v5 до внешнего отката. Его нельзя молча считать снимком начала новой установки. При отсутствии созданных объектов оно сохраняется отдельно, а v5.1 снимает текущие файлы и базу заново. Новые снимки и восстановление TIMESTAMP выполняются в UTC с отметкой в манифесте. Завершённый снимок установленного сайта не заменяется автоматически.
5. **Диагностика.** Добавлен закрытый журнал предупреждений include/require и фатальных ошибок. Аргументы стека удаляются явно, включая аргументы include, которые PHP 7.4 оставляет даже при `DEBUG_BACKTRACE_IGNORE_ARGS`. Посторонние тексты исключений в журнал не переносятся. Файл защищён PHP-ответом 404 и правами 0600; логирование не подавляет остановку.

Эти исправления не выдаются за установленную причину прежнего `nc_page.class.php`.

## Региональная настройка и ограничения

В свежих данных регион привязан к `medelta.clinic`, а сайт — к `dev.lifepodrostka.ru`. Автоматической подмены нет. Для проверки контактов домен существующей записи временно менялся через штатный редактор только на копии; откат восстановил исходное значение. Перед запуском нужно явно настроить `main_domain`, контакты и реквизиты своего региона.

Доставка внешних писем не проверялась. Намеренно пустые 18 черновиков не заполнялись. Особенности переполнения исходной вёрстки не маскировались новым CSS. Рабочий хостинг не изменялся. На PHP 8.3.36 свежая копия прошла проверку, но это не гарантирует исчезновение прежнего хостингового сбоя: для него при повторении нужен новый диагностический журнал.
