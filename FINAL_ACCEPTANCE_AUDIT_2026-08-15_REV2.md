## 2. Что подтверждено и не должно переделываться

### 2.1. Патч собран от правильной базы

Все семь файлов из `BASE_SHA256.txt` побайтно совпадают с файлами последнего архива панели. Следовательно, ZIP не собран поверх случайного или смешанного дерева.

### 2.2. Рандомизация

В production-коде больше нет обязательного требования, чтобы изменились одновременно desktop и mobile. Подтверждение строится по суммарной семантической дельте: достаточно не менее одной реально изменённой пары классов.

Для нового JSON/atomic updater:

- `ok:true` само по себе не заменяет доказательство изменения;
- проверяется фактическая semantic delta;
- 409/concurrent переводится в verify-only polling без второго mutating-вызова;
- проверка завершения публикации учитывает строгий успешный JSON-ответ либо свежий manifest;
- несовпадение `run_id` блокирует ложное подтверждение;
- пустой baseline manifest не считается свежим.

Для старых updater-версий сохранена прежняя модель совместимости: aggregate semantic delta `>= 1`, без навязывания нового JSON-контракта.

В архиве нет выдуманного production-файла `7k_atomic_v2.php`. Используется fixture `7k_atomic_REAL.php`, заявленная как копия реального updater.

### 2.3. Webmaster-IP

PATCH 047 не переписан и не обойдён. Typed GET-методы идут через общий `apiRequest`, а значит должны использовать тот же закреплённый source IP и тот же hard-stop при ошибке bind/mismatch. Fallback на произвольный IP не добавлен.

### 2.4. Новый recrawl-путь

В коде появился один фактический HTTPS-probe, результат которого повторно используется политикой редиректа и отправкой. Это устраняет прежнее расхождение, когда разные части стадии могли видеть разные результаты.

Разрешение редиректа теперь строится по фактам панели:

- host подтверждён артефактами Webmaster;
- redirect включён;
- конечный host действительно получен probe-запросом;
- конечный host входит в точный allowlist собственных редиректоров;
- read-back даёт допустимый HTTPS-ответ;
- suffix-подмена вида `dealredirectfast.com.evil.example` не должна совпадать.

Правки сайта и временные whitelist/bypass в `guard.php` для основной логики патча не нужны.

## 3. Критические блокеры

### Блокер 1. Реальная строка переобхода №232 не попадает в reconciliation

В последнем дампе присутствует фактическая строка:

- row: `232`
- job: `223`
- URL: `https://7k5281.casino/`
- status: `failed`
- `api_accepted=0`
- `task_id=NULL`
- `last_api_error_code=NULL`
- `last_error`: `Страница редиректит на чужой host dealredirectfast.com (ожидался 7k5281.casino)`

Селектор `RecrawlUrlRepository::findPendingOrStale()` выбирает failed-строки только при наличии одного из признаков:

- `last_error LIKE '%wrong_final_host%'`;
- `last_error LIKE '%WRONG_HOST%'`;
- `last_api_error_code='WRONG_HOST'`;
- `last_api_error_code='HOST_NOT_VERIFIED'`.

Фактическая строка №232 не содержит ни одного из этих признаков. Поэтому новый reconciliation её не увидит.

Тест W-05e не доказывает исправление инцидента: в тестовую ошибку искусственно дописано `(wrong_final_host)`, хотя в реальном дампе этого маркера нет.

**Обязательное исправление:**

1. Для новых ошибок сохранять отдельный структурированный `error_kind`, а не определять тип по тексту локализованного сообщения.
2. Для legacy-данных добавить безопасную нормализацию существующих сообщений, включая фактический формат из дампа.
3. Добавить тест на строке, идентичной реальной №232: без `wrong_final_host` в тексте и с `last_api_error_code=NULL`.
4. Никаких хардкодов `job=223`, домена или task ID в production-коде.

### Блокер 2. Для завершённой job reconciliation вообще не запускается

Последний дамп показывает, что job №223 уже завершена:

- `stage='done'`;
- `stage_status='ok'`.

То есть сайт фактически дошёл до конца. Проблема сейчас — stale-данные панели: строка №232 всё ещё `failed`, хотя Яндекс ранее вернул задачу `DONE`.

Новый reconciliation вызывается только внутри `runWmRecrawlStage()`. Dispatcher входит туда только когда текущая стадия равна `wm_recrawl`. Для job со стадией `done` этот код больше никогда не выполнится.

Следовательно, обещание «после установки реальная failed-строка станет accepted по данным очереди» для текущего состояния неверно.

**Обязательное исправление:**

1. Добавить независимый read-only reconciliation-механизм для stale recrawl-строк независимо от текущей стадии job.
2. Допустимые реализации: отдельная CLI-команда/maintenance worker/периодическая служебная задача панели.
3. Механизм должен делать только GET через закреплённый Webmaster-IP и обновлять локальные evidence-поля; повторный POST запрещён.
4. Он должен работать для завершённых и ушедших дальше job, а не только для `stage='wm_recrawl'`.
5. После установки один раз запустить этот общий механизм. Для job №223 переобход повторно не отправлять.

### Блокер 3. Installer меняет владельца production-файлов на `root:root`

В последнем архиве production-файлы имеют режим `0600` и владельца UID/GID `1001:1004`.

Текущий `install.sh`:

1. создаёт временный файл через `mktemp`;
2. копирует payload во временный файл;
3. перемещает временный файл на место production-файла.

`mktemp` создаёт файл `0600` владельца пользователя, запустившего installer. При запуске от root итоговый файл после `mv` становится `root:root 0600`. PHP-FPM/приложение под UID 1001 не сможет его прочитать. Root-проверка `php -l` после установки это не обнаружит.

**Это потенциальный полный отказ панели сразу после установки.**

**Обязательное исправление:**

1. Перед заменой сохранить UID, GID и mode каждого существующего файла.
2. До атомарного `mv` применить к временному файлу `chown --reference="$dst"` и `chmod --reference="$dst"` либо эквивалентную явную установку сохранённых метаданных.
3. Для новых файлов брать владельца/группу и безопасный mode от доверенного соседнего production-файла или каталога назначения.
4. Post-install smoke выполнять не только от root, но и от фактического пользователя приложения; минимум — проверять доступность всех установленных файлов для UID владельца действующего дерева.
5. Добавить installer-тест, который проверяет не только SHA, но и UID/GID/mode до и после установки.

### Блокер 4. Ручной rollback не восстанавливает изменения миграции 049

Installer сохраняет `rj_pre049.sql` и использует его при автоматическом compensating rollback. Но отдельный `rollback.sh` этот файл не выполняет.

Если миграция 049 перевела строку из `awaiting_user` в `pending`, явный откат вернёт файлы и часть схемы, но оставит изменённое состояние job. Это не полный rollback.

Дополнительно автоматический rollback подавляет ошибки восстановления через `|| true`, после чего может сообщить, что откат выполнен, даже если часть данных или файлов не восстановилась.

**Обязательное исправление:**

1. `rollback.sh` обязан fail-closed восстановить `rj_pre049.sql` до удаления служебных метаданных миграций.
2. Тест INSTALL→ROLLBACK должен содержать строку, реально подходящую под 049, и доказывать побайтно/попольно, что её исходное состояние восстановлено.
3. Убрать безусловное подавление ошибок восстановления.
4. При частичном откате выводить `ROLLBACK_FAILED/PARTIAL`, ненулевой exit code и точный список невосстановленных объектов. Нельзя писать «откат выполнен», если хотя бы одна операция не прошла.

### Блокер 5. Миграция 049 не охватывает фактические legacy-данные

Миграция требует наличия в `refresh_jobs.artifacts_json` нового поля:

`update_classes_stage.baseline_reason = update_classes_family_unresolved`.

Но это поле начинает записывать только код из нового патча. В последнем SQL-дампе `baseline_reason` отсутствует. Следовательно, data-fix 049 не возобновит ни одной старой зависшей job, ради которых он и создавался.

При этом фактическое legacy-доказательство уже имеется в `sites_managed.uc_detection_json`, где хранится причина `update_classes_family_unresolved`.

**Обязательное исправление:**

1. Либо построить миграцию 049 по существующим полям `sites_managed.uc_detection_json`/`uc_capability` и состоянию job.
2. Либо перед requeue выполнить детерминированный backfill нового `baseline_reason` из существующего detection evidence.
3. Сохраняются ограничения: только auto; execution не начат; attempts=0; исключить custom и disabled; не трогать completed/verified/operator-skip.
4. Тест должен использовать запись формы последнего дампа, в которой `baseline_reason` отсутствует.

### Блокер 6. Отсутствующий `added_time` может привести к повторному POST

`RecrawlReconciliationService` для совпавшего URL без локального task ID требует успешно распарсить `added_time` и попасть во временное окно. Если `added_time` отсутствует или не парсится, совпадение игнорируется и сервис разрешает POST.

По контракту Yandex Webmaster `added_time` — необязательное поле. Обязательными для задачи являются `task_id`, `url` и `state`. Поэтому валидная задача `IN_PROGRESS` или `DONE` без `added_time` может быть проигнорирована, после чего панель повторно отправит URL.

**Обязательное исправление:**

1. Точное совпадение URL с валидными `task_id` и `state`, но без `added_time`, должно давать `indeterminate/wait` либо безопасное принятие по явно описанной политике.
2. В этой ситуации повторный POST запрещён.
3. Для ограничения выборки использовать поддерживаемый API-параметр `date_from` и нормальную пагинацию.
4. Если достигнут safety-cap страниц и нельзя доказать отсутствие задачи, результат — `indeterminate/no POST`, а не `allow_post`.
5. Добавить тесты: `DONE` без `added_time`, `IN_PROGRESS` без `added_time`, невалидный `added_time`, задача за пределами первой страницы, исчерпанный safety-cap.

### Блокер 7. Заявленная полная регрессия не приложена как воспроизводимое доказательство

REPORT заявляет `47 suites` и `PASS=1181`, но `tests/TEST_STDOUT.txt` содержит вывод только нескольких целевых групп и install/rollback. Полного сырого вывода 47 suite в пакете нет.

В среде этой приёмки отсутствует PHP/MariaDB runtime, поэтому я не могу независимо повторить заявленный прогон. Статическая проверка и сопоставление с дампом выполнены, но цифры разработчика нельзя считать независимым доказательством.

**Обязательное исправление:**

1. В новый ZIP вложить команду единого test runner и полный необрезанный stdout/stderr.
2. Указать версии PHP, MariaDB, расширений и exit code.
3. Каждый acceptance ID должен иметь фактический результат, а не только упоминание в REPORT.
4. Обязательны отдельные тесты на все шесть блокеров выше.

---

### Задача

Исправить последний кумулятивный хотпатч Refresh Panel и передать один новый production-ready ZIP. Работать только со стороны панели. Файлы сайтов, `guard.php`, редиректоры и шаблоны сайтов не изменять.

Текущий ZIP не устанавливать: он содержит подтверждённые dump-backed дефекты reconciliation, installer и rollback.

### Неприкосновенные уже принятые решения

1. Рандомизация считается подтверждённой при суммарной semantic delta `changed_pairs >= 1`; одновременное изменение desktop и mobile не требуется.
2. `ok:true` не подменяет фактическую проверку delta.
3. Для 409/concurrent/timeout после единственного mutating-вызова работает verify-only polling; второй mutating-вызов запрещён.
4. Старые updater-family продолжают работать по aggregate delta без нового JSON-контракта.
5. PATCH 047 сохраняется: каждый Webmaster account использует назначенный source IP; bind/mismatch — hard stop без fallback.
6. Typed GET и POST используют один routed transport.
7. Собственный redirect разрешается только по фактам и точному allowlist, а неизвестный host блокируется.
8. Никаких хардкодов job ID, домена, Webmaster account ID, source IP или task ID.

### Обязательные изменения

#### A. Legacy recrawl selection

- Ввести структурированный тип ошибки для новых записей.
- Добавить нормализацию legacy-ошибок.
- Реальная строка с текстом `Страница редиректит на чужой host dealredirectfast.com (ожидался 7k5281.casino)`, `last_api_error_code=NULL`, `task_id=NULL`, `api_accepted=0` обязана попадать в stale reconciliation.
- Тест не должен дописывать искусственный маркер `(wrong_final_host)`.

#### B. Stage-independent reconciliation

- Реализовать общий GET-only reconciliation stale recrawl-строк, который запускается независимо от текущей стадии job.
- Он должен обрабатывать также `done`, `index_watching` и другие стадии после `wm_recrawl`.
- Для найденной в Yandex очереди задачи обновить локальные `api_accepted`, `task_id`, state, source и evidence идемпотентно.
- Не делать POST.
- Для текущего job 223 разрешён только GET-reconciliation; переотправлять URL нельзя.

#### C. Migration 049 legacy backfill

- Не требовать нового `artifacts_json.baseline_reason` для старых записей, где это поле исторически отсутствует.
- Использовать существующее `sites_managed.uc_detection_json.reason=update_classes_family_unresolved` либо выполнить детерминированный backfill.
- Requeue только auto + family_unresolved + not_started + attempts=0.
- Исключить custom, disabled, ambiguous, started, verified, completed, operator-skip и записи с attempts>0.
- Миграция идемпотентна и пишет точный audit count.

#### D. Safe reconciliation when `added_time` is absent

- Отсутствующий/невалидный `added_time` не даёт права на повторный POST.
- Точный URL с валидными `task_id/state` переводит решение минимум в `indeterminate/no POST`.
- Использовать `date_from` и пагинацию.
- При исчерпанном safety-cap — `indeterminate/no POST`.

#### E. Installer metadata safety

- Сохранить UID/GID/mode каждого заменяемого файла.
- До atomic rename применить метаданные исходного production-файла к временному.
- Новые файлы получают владельца/группу от доверенного production-соседа.
- Post-smoke должен доказать чтение файлов пользователем приложения, а не только root.
- Любое несовпадение BASE SHA, manifest, owner/mode или smoke — fail-closed до миграций либо compensating rollback.

#### F. Complete rollback

- Явный `rollback.sh` восстанавливает данные 049 из `rj_pre049.sql`.
- Автоматический и ручной rollback не подавляют ошибки.
- Частичный откат завершать ненулевым exit code с перечнем ошибок.
- INSTALL→ROLLBACK обязан вернуть файлы, UID/GID/mode, migration registry, settings, schema/evidence и строки jobs в исходное состояние.

5. `MANIFEST.sha256`;
6. `BASE_SHA256.txt` для всех заменяемых файлов;
7. `REPORT.md` с таблицей `требование → файл/метод → test ID → результат → evidence`;
8. единый test runner;
9. полный stdout/stderr тестов и exit codes;
10. точную canary-инструкцию.

Не передавать промежуточные ZIP и не объявлять готовность по component-тестам. Готовность объявляется только после прохождения stage-level, dump-shaped migration/reconciliation, installer metadata и full rollback тестов.

### Definition of Done

Релиз принимается, только если одновременно выполнено следующее:

- реальная форма строки №232 выбирается и reconciled без POST;
- reconciliation работает при job `done`;
- для job 223 отсутствует повторная отправка;
- новый и старый updater завершаются по реальному proof, достаточно одного изменённого класса;
- mutating call count не превышает 1;
- Webmaster source-IP routing сохранён для GET и POST;
- installer сохраняет фактические UID/GID/mode;
- rollback полностью возвращает данные 049 и не скрывает ошибки;
- все тесты имеют `FAIL=0`, `SKIP=0`, ненулевых необъяснённых exit code нет;
- canary проходит без изменения файлов сайта и без ручного пропуска стадий.

По последнему дампу job №223 уже находится в `done/ok`. Поэтому:

Упоминание job №223 здесь — не production-костыль и не требование хардкода. Это контрольная запись из фактического дампа, на которой обязана подтверждаться универсальная логика.

## 6. Решение по установке

До исправления блокеров 1–6:

**не запускать `install.sh` и не устанавливать ZIP на production.**

После получения следующего ZIP сначала повторить статическую/dump-backed приёмку, затем выполнить installer и canary на копии либо одном контролируемом экземпляре. Только после проверки владельцев файлов, source-IP, mutating counter и GET-only reconciliation разрешать общий rollout.
